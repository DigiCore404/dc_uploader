Workspace access

Manage your login and which IP addresses can reach this service.

One IP or CIDR range per line. Empty allows all IPs that can reach the service, with login still required. Requests outside the list are blocked, including the login page. Keep your current address allowed. Docker or a reverse proxy may show a shared gateway IP; per-device restrictions then need a host firewall or proxy policy.

New passwords need at least 12 characters. Saving signs out all sessions. Passwords are stored as salted hashes. For encrypted browser access, start the service with a TLS certificate and key.

Import torrent → automatic seeding
The selected client downloads the source. After all files are complete, the uploader publishes to DigitalCore and sends the confirmed torrent back to that same client through its API, using the matching parent folder. No shared watch folder is needed for this flow.
Set these defaults, then choose Import torrent, fill in the details and explicitly enable automatic publication. The service must remain running; your browser can close.
New upload / CLI → output watch folder
The confirmed .torrent is written to /watch. To seed automatically, configure qBittorrent to watch the same physical host folder. Its save location must be the parent of that release as seen inside qBittorrent.
Two containers both using the name /watch may still have different host mounts. This test does not verify watch-folder delivery. For releases in different parent folders, use the matching per-folder client configuration or add the confirmed torrent with the correct save location.
CLI & unattended uploads
The browser is optional. Use a qBittorrent completion command, a manual CLI upload or an optional incoming-folder watcher.
Starting the web service does not enable the CLI folder watcher.
Import automation handles only torrents you schedule in Import torrent. Folder automation starts only when you explicitly run the watch command below.
Install on a Linux seedbox without Docker
Extract the package into a folder you own and run the commands there. No root is needed when Python 3.10+, venv, FFmpeg and MediaInfo are already available. If system tools are missing, ask your seedbox provider to supply them; the optional install.sh --system-deps route needs sudo/root.
bash install.sh
Edit config.ini with your DigitalCore credentials and real seedbox folders. These are example paths; replace your-user with your account:
[Paths]
DATADIR = /home/your-user/media
WATCHFOLDER = /home/your-user/watch
Set your initial workspace login in [Web] before first startup, or use the temporary password printed in the terminal. Later login changes are made in Settings. Start the headless service:
bash start.sh web --host 127.0.0.1 --port 6080 --no-browser
On your PC, open an SSH tunnel using your normal seedbox account:
ssh -L 6080:127.0.0.1:6080 your-user@seedbox.example.com
Then open http://127.0.0.1:6080 in your PC browser. The uploader and media processing run on the seedbox. Keep the uploader process running. If your provider supports systemd user services, install the optional service without sudo:
.venv/bin/python scripts/service.py install --host 127.0.0.1 --port 6080
Startup without a logged-in session depends on the provider's user-service/lingering policy. Otherwise use their supported process manager. Configure the client's WebUI address in Clients, then save and test the real folder paths above. Docker and VNC are not required.
1. Upload one prepared release
From the extracted app directory on Linux, check setup and preview first. Replace the path and category with your own; --cat 6 means Scene/1080p.
bash start.sh check
bash start.sh upload /srv/media/My.Release --cat 6 --dry-run
bash start.sh upload /srv/media/My.Release --cat 6
The last command publishes immediately. Metadata flags, folder images and screenshot settings still work. On Windows use start.cmd instead of bash start.sh.
2. qBittorrent: run after download completes (one-shot)
Use this route when qBittorrent already downloads your releases. No incoming-folder watcher is needed. In the downloading client, enable “Run external program on torrent finished” and use this native Linux example (replace the install path and category):
/bin/bash /home/your-user/dc_uploader/start.sh completed "%F" --cat 6 --hash "%I"
%F is the completed content path; %I is the source torrent hash. This callback currently accepts a complete release directory inside DATADIR. A single loose video file is rejected; do not substitute its shared parent directory. Metadata uses folder/NFO images and your screenshot settings. The category applies to every callback.
The command runs where the downloading qBittorrent runs. A qBittorrent container cannot execute an uploader installed only on the host or in another container. This command requires the uploader and its Python/tools to be available in that environment. A remote WebUI connection alone does not make this command runnable.
Each source hash is recorded in SQLite before publication. Repeated callbacks do not repost it, including after a crash or failed attempt. Simultaneous callbacks wait up to 30 minutes for the uploader; keep logs and inspect failures before retrying. Do not enable a callback on the destination seed-client or run scheduled imports/folder watching over the same releases.
Separate DigitalCore seed-client
The original torrent remains in the download client. Successful CLI uploads write the confirmed DigitalCore torrent to WATCHFOLDER. Configure only your DigitalCore seed-client to watch that output directory. Give both qBittorrent clients access to the same media; no second download or copy is needed.
Host media:              /srv/media/downloads
Download-client media:  /downloads
DigitalCore-client media: /downloads
Release:                /downloads/My.Release
Seed-client save path:  /downloads
Uploader WATCHFOLDER:   /watch
The uploader and seed-client must mount the same physical torrent-output directory at their watch paths. Set that watched directory’s save location to the parent of the release as seen by the seed-client. With a flat library this is /downloads. Nested release parents need separate watch rules or manual/API addition with the correct save location. Let the client verify existing files. Adding a second connection in Clients only monitors it; scheduled imports currently return the new torrent to their selected import client.
3. Optional: watch a dedicated incoming folder
Create a dedicated incoming folder inside your content library, with one fully prepared release subfolder per upload. Every existing stable release subfolder there is eligible for publication. Do not point the watcher at your entire download archive or run it on the same folders as scheduled imports.
bash start.sh watch --cat 6 --folder incoming
This is a running process; keep it running in your service manager or terminal session. It uses the chosen category for every release and waits for files to stop changing (default 120 seconds, checked every 30 seconds). A stalled download can look stable: add completed content only. Attempts are stored in SQLite and uncertain/failed uploads are not automatically reposted.
4. Run CLI commands in Docker
From the directory containing compose.yaml, with the same volumes and config.ini as the web service:
docker compose run --rm uploader check
docker compose run --rm uploader upload /content/My.Release --cat 6 --dry-run
docker compose run --rm uploader upload /content/My.Release --cat 6
docker compose run --rm uploader watch --cat 6 --folder /content/incoming
The watcher command stays attached to your terminal. The example watches only /content/incoming. Set [Watch] INCOMING_DIR = incoming in config.ini to make this the default; --folder overrides it. Keep the data volume persistent and configure watch-folder seeding as explained above. CLI uploads, completion callbacks, folder-watcher uploads and browser uploads all appear in Activity, including logs and results. Confirm actual seeding in Clients.
